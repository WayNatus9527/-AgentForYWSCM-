## 5. 后续实现必须保持的不变量

1. **数量与承诺分开。** `g/q/d` 为良品/待验/残次；`r/t/h/b` 为订单占用/调拨预占/冻结/物理保留。当前 `available = g-r-t-h-b`，`unallocated = max(0, available)-offline-online-pending-withdrawing`；合法写入须同时保证非负。B 是物理保留，不是计划安全库存策略，不能重复扣减。
2. **额度转换不能双计。** 100 件渠道额度转成 30 件订单占用后应为 70 + 30；取消仅释放未履约量，按授权策略回补或释放。旧聚合额度不能未经核对自动分配给新来源账号。
3. **无余额不等于零库存。** 未建立可信基准的经营组合保持未知；已确认零库存且没有余额行的组合允许进入盘点。未知库存不能形成确定的缺货或补货结论。
4. **统一入账和完整事务。** 库存、单据、流水、事件及 Outbox 同事务提交，审批多行差异全部成功或全部回滚；不得在新模块直接更新余额绕过 `inventory.movement()`。
5. **请求重试与业务重复分别处理。** 请求键及内容指纹约束同键重试；业务凭证约束换请求键的重复。分批使用独立子凭证。同凭证内容变化拒绝，不能按相同商品和数量猜重复。
6. **缓存结果仍检查当前权限。** 停用、撤权、换岗位之后不能通过旧幂等结果读取未授权资源；Agent 和 Worker 同样受约束。
7. **盘点锁不被旁路。** 按商户、仓库、SKU 持久化锁定，阻止范围内实物和承诺变化。申请人、所有盘点人及提交人不能担任审批人。覆盖冲突保留锁并生成任务，关闭任务不会自动解锁；取消盘点只释放锁。
8. **质量数量保持专属。** 退货待验、已开始检验、已检待上架及待处置数量不可挪用。合格检验完成后仍在待验区，独立上架才增加良品。报废及新供应商退货须另一管理员批准。
9. **累计数量守恒。** 收货不超授权采购，退货不超原履约；在途＝累计发出－累计签收－已批准损失。发货后不能通过取消凭空恢复来源仓实物。
10. **证据追加保存。** 初盘、复盘、审批、任务及质量历史不覆盖；事件更正追加关联记录。未知实际时间保持未知，负时长暴露数据质量问题，不改成零。
11. **时钟与隔离不混用。** 业务期限可用虚拟时钟，认证、安全过期及实际耗时使用真实时间。`run_id` 与 `tenant_id` 各司其职，不能只靠命名或 SQL 过滤声称完成隔离。
12. **阶段迁移只追加。** 当前迁移 1—6 的含义保留。下一阶段预计新增迁移 7，提交前重新核对实际序列，不能重写已应用迁移来修复旧库。

兼容注意：旧 `/api/v1/quality` 保留“检验并上架”的合并动作；新工作台使用分步流程。旧 `/api/v1/returns` 的新供应商退货返回 `awaiting_review` 申请，HTTP 200 不代表已经扣库；升级前已完成请求的幂等回复继续保留。普通旧版无凭证收货/交货默认禁止新增，只保留历史请求重放及显式迁移兼容档位。

`run.sh` 在首次启动时显式初始化本地演示资料，再启动业务服务；已有数据不会因正常重启重新导入。新机器按 README 创建虚拟环境并安装依赖，另行初始化模拟控制目录，不能期待 Git clone 带有本机数据库或账号文件。

### 7.2 现有运行与版本绑定

| 运行 | 用途 / 结果 | 当前可用边界 |
| --- | --- | --- |
| `dev-workbench` | M2 开发数据，seed 20261017，登记为 passed | manifest 绑定旧代码哈希 `25db6a74…`；当前 v0.7.0 不能直接继续运行它 |

当前 CLI `create` 和管理页普通生成功能走 M2 场景；M3 工作流使用 `verify_m3.py` 或 `Control.create(..., m3=True)`。接手时可用以下命令创建独立的 M3 开发数据，避免复用旧演示库：

上一步会执行一份 M3 演示流程并生成业务账号。将下例 `RUN_ID` 换成列表中的实际运行编号，在空闲端口启动：

mkdir -p .local/handoff-verification

### 8.2 配置边界

### 8.3 备份、迁移和恢复

1. 升级前保留代码提交、配置及备份；记录原余额、单据、流水、授权和运行身份。
2. SQLite 使用在线备份工具，获得数据库文件及同名 JSON 校验清单；不要把运行中的 WAL 数据库当成普通文件随意复制。
3. 新迁移仅追加；应用启动自动执行已登记迁移。迁移后核对原业务内容及新旧契约回归。
4. 恢复演练在全新目标文件/数据库中进行；已绑定数据库不能直接换路径复用。恢复后旧会话失效，新环境重新绑定，历史事件的原运行标识保留。
5. 回退使用升级前备份及对应代码；不承诺数据库可以自动降级。完整模拟空间还需保留 manifest、输入、轨迹、私有事实与报告。

```sh
# 新建标准备份：输出文件名、哈希及清单
.venv/bin/python -m app.backup create --directory "$PWD/.local/backups/handoff"

# 将路径换成上一步的实际备份和一个从未存在的目标文件
.venv/bin/python -m app.backup restore --source /absolute/backup/inventory-example.db --target /absolute/new-restore/inventory.db
```

`restore` 要求源数据库旁存在同名 `.json` 清单。第 6 节的 M3 升级快照由升级脚本保存，核验依据是部署记录，不能直接假定它具备上述工具所需的清单；常规迁交优先重新生成标准备份。恢复验证不能覆盖当前使用中的业务数据库。

- [ ] 操作说明、已知限制、容量实测与未覆盖内容；GitHub 同步按对应任务执行。

PRD 提出每次合并固定场景及不少于 10 组随机种子、阶段不少于 100 组额外种子、版本累计不少于 1,000 组；这些是验收预算与门槛，不能仅用种子数代替边界覆盖。本机历史资源基线为 ARM64、8 个逻辑 CPU、16 GiB 内存；正式容量验收前重新记录机器、数据分布、并发和时间预算。中型目标查询 P95 ≤2 秒、单项写入 P95 ≤3 秒尚未宣称达成。

接手后仍需明确的执行参数包括：阶段负责人及投入、采购/运营/分析岗位权限、业务工作日历和经营参数范围、固定仓库分配顺序、连接账号的字段映射、种子与容量预算，以及将来的真实接入范围。已实施的 M3 范围锁定与双人审批作为当前基线保留；改变它们应记录需求变更及补跑场景。人员和预算未确定前，不将工作包顺序换算成承诺日期。
