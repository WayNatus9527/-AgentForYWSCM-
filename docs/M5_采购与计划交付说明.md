# M5 采购与计划 · v0.9.0

承接 M4，迁移 8 新增 12 张表。采购承诺、分批运输及确定性补货已接入本地工作台；仅使用模拟数据，不发送真实采购通知或付款。最终测试、种子及报告哈希见 [验收摘要](M5_验收摘要.json)。

## 操作流程

1. 在基础资料维护供应商和供货商品。在「采购与运输计划 → 采购计划」创建多商品计划，录入下单时间及承诺到货时间。未知时间可留空；变更承诺必须有凭证和原因，原始承诺始终保留。已建运输批次有自己的预计到达时间，改变主单承诺不会悄然改写这些批次。
2. 对计划行创建到货批次，登记承运方、方式、运单和预计时间。登记本批发出后，可分次签收良品、待验及残次。系统限制累计实收，超收拒绝。实际时间和登记时间分别留存。
3. 待验货从具体到货凭证「开始本次到货检验」，再到「检验与处置」完成检验、分批上架。普通质检不能挪用这些专属待验量。实收、当前待验、累计曾可用分别展示，累计曾可用不代表现存良品。
4. 退供应商沿用原收货凭证和另一管理员审批；原采购实收不回退。新建补发采购时，选择已执行的退货单，并保持供应商、商品和收货仓一致。累计关联补发不超过该次实退数量，原单、退货、新供给可追溯；关闭补发计划也不自动释放这项历史上限。
5. 「检查采购延期」按每条供给行更新唯一异常任务。后续到货、承诺变更和关闭余量更新影响量；任务处理历史保留，不以清除任务改变库存。关闭剩余计划前，先取消所有未发批次；已发在途仍可继续签收。关闭不能使有效销售供给关联超过剩余供给，须先核实并解除多余关联。
6. 「分批调拨」创建计划后，按本次可发量建立独立批次并预占。一个批次发出全部已预占量，分多次发出应建多个批次；每批允许分次签收。取消仅释放未发批次，不能把已发货恢复来源仓实物。
7. 在途短少或已核实的拒收损失按批申请，由另一管理员批准核销。仍在退运的货物不能当作损失；已到破损品按残次签收。审批期间批次新增签收会使原申请过期，需要驳回后重新核实；一批差异不关闭其他批次。

## 规则补货

在「规则补货」设置仓库、商品、供应商、需求窗口、覆盖天数、提前期、目标安全量、最小采购量与包装倍数。登记已经结束业务日的需求数量及来源凭证，明确的零需求可以录入，缺日不能自动填零。需求证据保持不可变；异常或未知日会阻止确认。

当前规则 `replenishment-v1`：

- 覆盖期预测 = 向上取整（窗口需求总量 ÷ 窗口天数 ×（提前期 + 覆盖天数））。
- 预测已含现有订单时，需覆盖量 = max（预测、未履约订单）− 已预占订单量；未含时，需覆盖量 = 预测 + 未履约订单 − 已预占订单量。
- 净补量 = max（0，需覆盖量 + 目标安全量 − 未分配现货 − 可信及时供给）。非零结果先满足最小采购量，再向上凑齐包装倍数。

库存已经扣除订单预占、调拨预占、渠道额度等承诺，因此需求侧同步去掉已扣库存的订单预占。安全量是计划目标，不直接增加物理保留 B。多仓订单的未分配需求归属其固定第一仓，已分配量归属实际预占仓。

采购和调拨供给拆成互斥的未分批计划、未发批次、在途；签收入库即退出未来供给。未预占调拨、交期未知、逾期和覆盖期外供给只列风险。历史旧单缺少交期时也保持未知，不猜测到达日。

计算会保存完整输入、版本、需求日、供给阶段、规则和建议。缺日、异常需求、未知库存、停用策略/经营关系、缺少订单权限时显示依据不足，不能把未知当作零采购。方案创建者可在真实时间 30 分钟内修改确认数量并填写理由；确认重新检查当前权限与全部输入。正数须满足最小采购量和包装倍数；填 0 表示明确不采购。

确认、创建采购、写入决策在同一事务内完成，重复确认返回同一采购；如果输入变化则要求重算。旧快照保留历史，不作为当前库存或供给的实时承诺。

## 兼容、权限与接口

管理员、仓管可操作；运营、分析可读取授权范围。收银岗位无计划权限。仓库权限、租户隔离、CSRF、请求幂等和业务凭证去重继续生效，缓存重放前也复查权限。差异必须独立管理员复核。涉及连接成员权限的订单依据在查看快照时重新授权。

新供给单拒绝旧采购收货/关闭、整体调拨和旧差异接口绕过批次。旧单保留原操作流程；旧 Agent 辅助建单仍使用原契约，M6 再整合新的解释和执行跟踪。

| 接口（`/api/v2`） | 用途 |
| --- | --- |
| `POST /purchase-plans`、`/transfer-plans` | 创建多行计划；采购可带 `replacement_return_id` |
| `GET /supply-orders/{purchase\|transfer}` | 分页读取主单、批次、到货及历史 |
| `POST /purchase-plans/{id}/promise`、`/purchase-plans/scan-delays` | 承诺变更、延期检查 |
| `POST /supply-orders/{kind}/{id}/batches`、`/close` | 分批计划/预占、关闭未分批余量 |
| `POST /supply-batches/{id}/{ship\|receive\|cancel\|discrepancy}` | 发出、签收、取消及差异申请 |
| `POST /supply-discrepancies/{id}/review`、`/supply-receipts/{id}/inspect` | 独立复核、来源检验 |
| `GET /planning/{policies\|plans\|demand}` | 分页策略、计算记录和需求历史 |
| `POST /planning/demand`、`/planning/policies` | 需求登记、版本化策略 |
| `POST /planning/policies/{id}/calculate`、`/planning/plans/{id}/confirm` | 冻结计算、人工确认 |

详细字段见 [OpenAPI](openapi.json)。迁移 8 表结构见 [PostgreSQL DDL](schema-postgresql.sql)，不可将参考 DDL 代替迁移器的历史保护和运行绑定。

## 复现与证据

```sh
.venv/bin/python scripts/verify_m2.py --mode pytest --test-path tests --root /absolute/new-test-root
.venv/bin/python scripts/verify_m5.py --count 100 --root /absolute/new-m5-validation-root
.venv/bin/python scripts/verify_m2.py --mode postgres-suite --test-path tests --count 10 --m3-count 10 --m4-count 10 --m5-count 100 --root /absolute/new-postgresql-root
```

受控模拟要求 macOS 系统沙箱，PostgreSQL 需 `requirements-pg-test.txt`；控制根目录必须为绝对路径。需要外层工具沙箱授权时，保留模拟器自身隔离，不关闭它。每轮使用新目录、新种子；失败证据保留，开发数据不得混入独立验收。

`scripts/verify_m5_browser.cjs` 使用 Playwright、本机 Chrome、全新 M5 development 运行、其 `business/login.json` 和输出目录。脚本会修改该开发库，覆盖采购、检验、关联补发、分批运输、独立复核、补货确认、岗位视图及桌面/手机布局；不可指向验证或真实业务库。

`scripts/verify_m5_upgrade.py --source /path/to/m4.db --output /absolute/new-upgrade-directory` 只在线备份源库，再升级副本、逐表比较、二次迁移、备份恢复并重新绑定。源库不会升级。迁移 1—7 不改写；迁移 8 在本阶段开发期间定稿，开发中间库不直接复用，必须创建新运行或受控后继空间。
