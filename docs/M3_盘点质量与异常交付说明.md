# M3 盘点、质量与异常交付说明

产品：跨境电商供应链管理Agent助手  
版本：v0.7.0；数据库迁移：6  
范围：PRD v2.0 的 FR08 增强、FR09、FR10、AT05。全部开发和验收使用模拟数据，无需模型密钥。

## 使用入口

业务工作台新增 **库存盘点、检验与处置、异常任务**。原有退货页面的“开始检验”和“退供应商”也进入新流程。模拟管理页仍使用独立账号和数据库，不与业务登录混用。

### 盘点

1. 管理员或仓管创建盘点单，选择已建立库存基准（包括已确认零库存）的仓库与 SKU，最多 100 个组合。
2. 确认范围，再开始盘点。系统在同一事务中保存账面快照并建立持久化范围锁。
3. 录入每行良品、待验、残次的实盘数量。存在差异须附处理意见和证据引用，且必须复盘。
4. 每轮复盘保留原始记录；提交后，由不同于申请人、各轮盘点人和提交人的另一管理员审批。
5. 全部差异在同一事务中记入单据、库存、流水、Outbox 和业务事件，同时释放锁。无差异不生成零差异库存流水。

锁定范围内，收货、交货、采购收货、调拨、质量处置、通用调整以及渠道额度/订单占用变更都受统一入账边界限制；范围外可以继续作业。API、模拟 Worker、既有 Agent 建单后的审批共用此边界。已完成命令的只读重试可返回原结果。

实盘不足以覆盖既有承诺或受保护质量数量时，盘点进入“冲突待处理”，保留全部锁并生成唯一异常任务，不产生部分入账。可以复盘后重新提交；确需先处理其他业务时，先取消盘点，处理完毕后创建新盘点单。取消只释放锁，不修改数量。审批驳回也保留锁，等待复盘或取消。

### 退货与检验

- 客户退货沿用原交货单关联和累计上限。凭证跨请求去重，同凭证内容变化会拒绝。
- 检验批次记录实际开始、完成和后续处置。一个退货单可以分成多批；未完成部分继续待验。
- 新检验流程中，合格品仍留在待验区，形成专属“已检待上架”数量；**重新上架**后才增加可分配良品。残次形成专属待处置数量。
- 普通质检、调整、盘点和其他退货不能挪用退货待验、已开始检验、已检待上架或待报废数量。
- 报废须先申请，再由另一管理员审批。供应商退货关联原收货单并经另一管理员审批，批准后才扣库；累计上限在申请及批准时检查。
- 处置申请冻结申请时的库存版本。等待审批期间库存若已变化，应驳回并按最新数量重新申请，使用新的处置凭证号。
- 标准原因分类、缺陷分类、责任对象、处理意见和证据引用均保存。附件本期保存引用编号，不提供附件文件上传服务。

兼容说明：旧 `/api/v1/quality` 仍保留明确的“检验并上架”合并命令，新增检验完成与上架事件；不会捏造过去的检验开始时间。新工作台统一使用分步流程。旧 `/api/v1/returns` 的供应商退货现在返回 `awaiting_review` 申请，调用方不能再把 HTTP 200 视为已经扣库。历史已完成单据及幂等回复不改写。旧历史数据缺失的原因或业务发生时间保持未知。

首版不自动执行退款、应付、索赔或财务结算。

### 异常任务

盘点覆盖冲突、检验残次自动生成关联任务，也可人工登记库存单据、退货、盘点和检验的异常。任务按商户＋业务对象＋规则＋异常实例唯一；数量、期限及规则版本变化追加历史，重复扫描相同内容不反复新增任务。

流程为待分派 → 处理中 → 待复核 → 已关闭；支持暂停、恢复、驳回、重开。负责人必须有相关仓库权限。普通任务可由负责人填写结果后结案；高优先级、盘点冲突或涉及人员责任的任务必须由另一管理员复核。人员责任必须明确勾选复核确认。后续指标更新不能覆盖已审核的处置证据，也不能悄悄降低复核要求。

超时按当前业务时间显示，并可显式执行“检查超时”生成一次提醒；不会据此认定丢货或人员责任。本期没有后台自动提醒调度。任务关闭不调整库存，不释放盘点锁。

## 数据与事件

迁移 6 仅新增盘点、锁、观察历史、异常任务、质量批次、质量处置及凭证表。迁移 1—5 的定义保持不变。盘点观察、盘点历史、任务历史和质量历史在 SQLite / PostgreSQL 上安装禁止更新、删除的触发器。

新事件关联仓库、SKU、业务对象、盘点行、任务、规则版本、原因和证据。记录业务时钟、请求上下文和计划处理期限，为后续瓶颈复盘提供事实；本期不输出因果归责或瓶颈诊断结论。

主要接口：

| 接口 | 用途 |
| --- | --- |
| `/api/v2/counts` | 创建、分页读取及各阶段操作 |
| `/api/v2/counts/{id}/observations/{initial,recount}` | 不覆盖历史的盘点观察 |
| `/api/v2/count-locks` | 当前授权范围内的持久化锁 |
| `/api/v2/inspections` | 检验批次开始、完成、上架、取消 |
| `/api/v2/quality-dispositions` | 报废或退供应商申请与复核 |
| `/api/v2/exceptions` | 唯一异常实例、指标历史和处理流程 |
| `/api/v2/exceptions/remind` | 生成超时提醒，保持业务状态不变 |

所有写接口使用登录、CSRF、岗位及仓库权限、幂等请求编号和版本检查。缓存回复返回前仍重新检查当前资源权限。完整定义见 `docs/openapi.json`。

## 模拟验收与复现

开发数据、固定回归、额外验证分别生成；每次运行独立进程、数据库/Schema、文件目录、账号、运行指纹和不可变 manifest。M3 额外数据包含两个商户、变化的 SKU/仓库规模、盘点盈亏、承诺覆盖冲突、不同检验结果、分批上架及双人处置。独立数量判定器不导入业务代码，另有手工算例校验。

```sh
# 全量回归（包含受管理子进程测试，本机 macOS）
.venv/bin/python scripts/verify_m2.py --mode pytest --test-path tests --root /absolute/test-root

# 额外 100 份 M3 数据，使用此前未用过的种子
.venv/bin/python scripts/verify_m3.py --count 100 --root /absolute/m3-validation-root

# PostgreSQL 全量回归，再各生成 100 份 M2 与 M3 数据
.venv/bin/python scripts/verify_m2.py --mode postgres-suite --test-path tests --count 100 --m3-count 100 --root /absolute/pg-validation-root
```

每次使用新的验证根目录。M3 验收运行完整业务流程，失败样本及报告会保存；重跑通过“重置”创建后继运行，不原地改写失败证据。M2 的事件时间切片、故障轨迹重放继续保留；M3 完整流程暂不支持时间切片或按捕获轨迹重放，界面/接口会明确拒绝这两种操作。

最终数字、种子、覆盖分布和报告哈希见 `docs/M3_验收摘要.json`。开发调试曾发现模拟脚本中一处请求编号过短，及浏览器脚本等待登录、选择已消失按钮的问题，已修正并保留失败记录；最终独立验证重新生成数据。

## 交付边界

本阶段保持模块化单体和原有库存口径。锁使用既有商户事务串行化配合范围记录，尚未声称适合高并发大规模生产。验收覆盖小规模多样数据及两种数据库，不等于容量压测。受管理进程隔离仍依赖 macOS 沙箱。

下一阶段 M4 是订单履约、Inbox 与连接器边界；计划补货和瓶颈分析分别属于后续 M5、M6。
